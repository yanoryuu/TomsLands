# balance-panel — マスタを直すときの進め方

2026-10-30 にユーザーが決めた手順。**一人で案を出してそのまま入れない。** 分析 → 複数の案 → 採点 → ユーザーが選ぶ、の順に進める。

## 前提（毎回確かめる）

- 目標は memory の [[bankruptcy-rate-target]]・[[village-progression-target]] と `Docs/Balance_Change_Log.md` の冒頭にある。
  - 破産: 理解している普通の人 1〜2 割、上手い人 0〜5%
  - 村: 最大まで普通 30 本・上手い 20 本
  - 設備の強化: 3〜4 日で元が取れる
- 値の置き場所:
  - スプレッドシート `1ddnBuVo11t7i7O3vD2ehTM44_0IAA7iZ19fasfw_p4k`
  - GAS（clasp）で Firebase の `config/production` に上がる
  - **体験版も同じ設定を読む**
- データ:
  - 人格マラソンのログ: `Recordings/marathon_*/progress*.log`、`persona_log_*.jsonl`、`consult_log_*.jsonl`
  - Unity のログ: `%LOCALAPPDATA%\Unity\Editor\Editor*.log`
  - 集計スクリプト: `D:\WorkTree\TomsLands\_scratch_wt04\tuning\`、`analysis_1030\`
- **測る期間をそろえる。** 値・C#・AI を変えた時刻より後の周だけを数える。変更の前後を混ぜない。

## 手順

```
- [ ] 1. 分析（エージェント 1 人、読むだけ）
- [ ] 2. 問題点を P1, P2 … の一覧にする
- [ ] 3. 審議（ワークフロー: 3 人が案を出し、2 人が採点）
- [ ] 4. ユーザーに点数表と進め方を見せ、入れる案を選んでもらう
- [ ] 5. 入れる（シート／C#）→ アップロード → 確かめる → 変更ログ → コミット
- [ ] 6. 決めた周数を回して測り、次の 1 に戻る
```

### 1. 分析

- 読むだけのエージェントを 1 人出す。範囲は今の値になってからの周に限る。
- 次の領域ごとに 0〜100 点を付けさせる:
  - 破産率・序盤の厳しさ・終盤の伸び
  - 配信の経済・設備・地図・イベント
  - ランク・村の育ち方・戦略の多様性
- あわせて出させるもの:
  - 確からしさ（標本の数）と、データの偏り
  - バグに見えるもの
- 採点の目安: 目標どおりなら 100。目標の幅 1 つ分外れるごとに −30。「ほぼ一択」の仕組みはさらに減点する。

### 2. 問題点の一覧

- 分析の指摘を「P1. …」の形で短く書く。数字・コードの場所・分かっている制約も添える。
- 自分の推測は推測と書く。
- 前の変更（バグの修正・セーブのリセット）で崩れた前提があれば、それも問題点に入れる。

### 3. 審議（ワークフロー）

このフォルダの `panel.js` を Workflow ツールで動かす（`scriptPath` に渡す）。`args` は次の 3 つ。

- `brief`: 下の「審議に渡す前提」を埋めた文
- `problems`: 2 の一覧
- `scratchDir`: 例 `D:\\WorkTree\\TomsLands\\_scratch_wt04\\panel_<日付>\\`

中身:
- 案を出す 3 人: 経済・データ、プレイ体験（読み→賭け→的中→大儲け）、慎重・段取り
- 採点する 2 人: A はコードとデータで裏を取る役、B はプレイ体験と本番への危なさを見る役
- 採点: 根本を直すか・根拠・プレイ体験・危なさと手間の 4 つを各 25 点で付け、合計 100 点

**審議に渡す前提**（毎回埋める）
- ゲームの芯と、ユーザーの目標（上の「前提」）
- 今の値と、変えた履歴（`Docs/Balance_Change_Log.md`）
- データの場所と、どの時刻からの周を数えるか
- 決まっていて動かさないこと（例: 設備は 3〜4 日で元が取れる、損のイベントは 3 倍にした、など）
- C# を直すときはマラソンの一時停止が要ること

### 4. ユーザーに見せる

- 点数の高い順の表を見せる。列は「点・案・種類（シート／C#／集計／変えない）」。
- 入れない案と、その理由を見せる。
- 審査役 2 人が一致した進め方を見せる。順番は「今／次に止めたとき／リセット後／あとで」。
- **審査役の意見が割れたところを、ユーザーが決める点として出す。**
- 自分の前の見立てが間違っていたら、そう書く。
- ユーザーが選ぶまで値は変えない。

### 5. 入れる

1. **C# を直すとき**
   - `tools/persona_play/marathon/pause.ps1` を実行し、progress ログに「一時停止」が出てから直す。
   - 直したら、コンパイル → EditMode テスト → `resume.ps1`。
   - 新しいキーは、まず今と同じ動きになる既定値で入れ、効き方はシートで動かす。
2. **シート**
   - 値を書き換えて、`clasp -u tokotom -P D:/WorkTree/TomsLands/_scratch_wt04/gas_clasp run apiUploadGameConst`（または `apiUploadBalance`）でアップロードする。
   - 公開の JSON を取り直して、値が入ったか確かめる。
   - 新しい値が効くのは、アップロードから 2 本目のランから（設定の取り込みの都合）。
3. **記録**
   - `Docs/Balance_Change_Log.md` に、時刻・シート・キー・前・後・理由を書く。体験版に届くかどうかも書く。
   - `_scratch_wt04\tuning\tuning_log.md` にも書く。
   - コミットする。
4. **報告**
   - 何を、なぜ変えたかを報告する（アップロードしたことを含む）。

### 6. 測る

- 審議で決めた指標と周数（ふつう 20〜30 周）を回してから、次の分析に進む。
- 足りないうちに次の変更を重ねない。
- 同時に変えるものは、指標が分けて読めるものだけにする。
