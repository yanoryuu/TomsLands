## 0. 目的

「需要度の高い商品を上から買う」ゲームを、「**数字が動く前に仕込む**」ゲームに変える。
そのために、需要変動の原因を**事前に紙面で公開**し、プレイヤーに推論させる。

**成功条件**: 仕入れ画面の数字だけでは最適解に届かず、朝刊を読んだ側が有利になること。

## 1. 確定した設計判断

| # | 判断 | 内容 |
|---|---|---|
| D1 | 記事の書き方 | **原因だけ書く（推論型）**。効果・数値・銘柄名は書かない |

## 3. 用語

| 用語 | 定義 |
|---|---|
| 号 | 1ターン分の紙面。新聞社ごとに発行される |
| 面 | 号の中のページ。一面 / 二面 / 市況 / うわさ |
| lead | 記事の掲載ターンから効果の発効ターンまでの間隔（ターン） |
| duration | 効果が維持されるターン数 |
| hype | 掲載ターンに即座に乗る価格倍率。真偽に関わらず発生する |
| 決着 | 発効 + duration を過ぎ、効果が終了した状態 |
| 確認 | 決着した記事の真偽を有料で開示すること |

**確定値**

| companyId | 社名 | price | 契約 | 信頼 | 速報 | lead | 誤報率 | 面 | 本数 |
|---|---|---|---|---|---|---|---|---|---|
| royal | 王立官報 | 20,000 | 5T | 5 | 1 | 1 | 0.00 | front | 2 |
| guild | 冒険者ギルド報 | 15,000 | 5T | 4 | 3 | 2 | 0.05 | front,second,market | 6 |
| commerce | 週刊商業新聞 | 12,000 | 5T | 3 | 3 | 2 | 0.10 | front,market | 4 |
| tabloid | 街角かわら版 | 6,000 | 5T | 1 | 5 | 3 | 0.35 | front,rumor | 5 |
| craft | 職人季報 | 6,000 | 5T | 4 | 2 | 1 | 0.05 | front | 2 |

**1ターンの分量**: 枠1で 2〜6本、枠3で最大15本。ただしクロスリファレンスで同一事象を複数社が報じるため、
**実際の事象数は1ターン4〜6件、うち効果を持つのは2〜3件**。読む量は増えても判断すべき件数は増えない。

- **網羅バー = 保有する面の数**。UI の物量とステータスを一致させる
- **料金と速報性は逆相関**。高い紙は裏を取ってから出すので遅い
- lead の上限は 3。`GameFlowGenerationSettings.cs:21-23` より戦闘間が最短2ターンのため、4以上は成立しない

| headline | string | 見出し |

## 5. 因果の3法則

推論型が成立する前提。**この3法則は絶対に一貫させる**。ブレると推論ではなく当てずっぽうになる。

| 法則 | 内容 | 既存の根拠 |
|---|---|---|
| L1 攻 | 敵の属性 → その弱点属性の**武器**が売れる | `dungeons.tsv` の `requiredAttribute` |
| L2 守 | 敵の属性 → それを防ぐ属性の**防具**が売れる | `items_sheet.tsv` の説明文（「水流の鎧＝火ダメージ無効」等） |
| L3 客 | 勇者のレベル・資金 → `requiredLevel` の高い高額品へ移る | `HeroLevelData` / `HeroPurchaseHistory` |

**相性表は常設のUI（図鑑）で参照できること。** 手元に表がない推論は記憶ゲーになる。

置き場は**どの画面からも開けるオーバーレイ**とする（常設ボタンで呼び出し、フェーズ遷移を伴わない）。
新聞を読むときも仕入れ銘柄を選ぶときも参照したくなるため、専用画面にすると遷移が増えて推論が記憶ゲーに戻る。
解説文そのものは預言者のダイアログ資産を流用してよい。

`Assets/Scripts/Newspaper/` に新設。

| クラス | 責務 |
|---|---|
| `NewsArticleData` / `NewspaperCompanyData` | マスターのランタイム表現 |
| `NewsScheduler` | 周開始時に**シードから発行カレンダーを一括生成**（静的・純粋関数） |
| `NewsModel` | 今ターンの号、予約中の効果、既読状態 |
| `NewsEffectResolver` | 有効な効果を集計し `TrendBias(itemId)` / `DemandKick(itemId)` / `HypeRate(itemId)` を返す |
| `NewspaperSubscriptionModel` | 契約、購読枠、契約残ターン |
| `ScrapbookModel` | ピン留め記事、決着状態、確認済み判定、社の実測的中率 |
| `NewspaperPresenter` / `NewspaperView` | 画面 |
| `PaperPageView` / `ArticleCellUI` / `CompanyCardUI` / `ScrapCardUI` / `MarketTickerRowUI` | 部品 |

`GameLifetimeScope` に登録し、`stateManager.RegisterOnEnter(TomsShopGamePhase.Newspaper, Entry)`。

### 6.1 発行カレンダー

毎ターン RNG で引くと「何も起きない周」が出る。**周開始時にシードから一括生成**して、読める起伏を保証する。

- 入力: 周のシード（`FlowSeed` を流用）、`GameFlow` のノード列。購読とは無関係に**全社分**を生成する
- 保証: 1周あたり大事件2回 / 属性トレンドの波3回 / 誤報は各社の `falseRate` に従う
- `truth = true` の事象は `crossRefGroup` 内の複数記事を**別の社・別の面に散らして**配置する
- `truth = false` は**単独記事**にする（＝1紙でしか報じられていない記事は怪しい、が成立する）
- シード保存だけで再現できる（記事本文はマスターなので保存不要）

## 7. 効果の適用

### 7.1 2段効果モデル

仕入れ値と売値は同一（`BlackSmithPresenter.cs:362` が `CurrentPrice` をそのまま使う）。
したがって「噂で買って事実で売る」がそのまま成立する。

| 段 | タイミング | 内容 | 真偽との関係 |
|---|---|---|---|
| 1段目 | **掲載ターン** | 価格 × `hypeRate`（1.00〜1.08） | **真偽に関わらず発生**。皆が紙面を読んで飛びつくため |
| 2段目 | **掲載 + lead** | `trendDelta` と `demandKick` が発効し `duration` 継続 | `truth = false` なら**発生しない** |

**誤報 = 1段目だけ来て2段目が来ない。** プレイヤーは高値掴みし、価格は数ターンかけて戻る。

`hypeRate` は記事の派手さ（面）に比例させる。**一面ほど高く買わされる**ので、うわさ欄で拾えた側が一番儲かる。

| 面 | front | second | market | rumor |
|---|---|---|---|---|
| hypeRate | 1.06 | 1.04 | 1.03 | 1.02 |

### 7.1.1 効果量の目盛り（3段階）

`Demand += (naturalDemand − Demand) × 0.15` の収束速度から逆算した初期値。

| 規模 | trendDelta | demandKick | duration | 3ターン後の需要変化 |
|---|---|---|---|---|
| 小 | 0.3 | 0.03 | 3 | 約 +0.06 |
| 中 | 0.6 | 0.06 | 4 | 約 +0.13 |
| 大 | 1.0 | 0.10 | 5 | 約 +0.21 |

「大」で需要 0.5 → 0.71 となり `highDemandThreshold = 0.7` を跨いで価格レンジが上がる。
**大事件だけが価格レンジを跨ぐ。** duration の上限は 5（Medium が 8〜16ターンのため）。

### 7.2 `ItemModel.ApplyShopTurnEconomy` への接続

現状（`ItemModel.cs:364-391`）:

```
Trend         += Random(-trendDriftMax, +trendDriftMax) - Trend * trendDecayRate
naturalDemand  = 0.5 + Trend * trendAmplitude              // 0.30 → 0.2〜0.8
Demand        += (naturalDemand - Demand) * trendConvergenceRate   // 0.15
```

収束が 15%/ターンなので、`Trend` を動かすだけでは lead 1〜3 の窓では体感に届かない。
そのため**2成分**にする。

- `TrendBias` は **`runtime.Trend` に加算しない**。ランダムウォークの減衰と干渉し、期間終了時に剥がせなくなるため。
  別枠で保持し、`naturalDemand` の計算時にだけ足す。

```
effectiveTrend = Clamp(runtime.Trend + resolver.TrendBias(itemId), -1, 1)
naturalDemand  = Clamp01(0.5 + effectiveTrend * settings.trendAmplitude)
Demand        += (naturalDemand - Demand) * settings.trendConvergenceRate
Demand        += resolver.DemandKick(itemId)     // 発効ターンのみ、1回だけ
```

`ShopEconomy.md` の Step 構成に **N1: ニュース予約効果の適用** としてアイテムループの前に追加する。

価格側は `newPrice` 確定後に `* resolver.HypeRate(itemId)` を掛け、既存の Floor / Ceiling クランプに通す。

### 7.3 市場モデルとの関係

`feature/jev-market-sim` の2層モデル（適正値 × 相場の揺らぎ）に対し、役割が分かれる。

| 層 | 担当 | ニュースの効き方 |
|---|---|---|
| 層1 適正値 | `ShopFairValue.Compute`（需要から算出） | **2段目**（trendDelta / demandKick）がここを動かす |
| 層2 揺らぎ | `LocalAbm` の λ / `MarketHeat` | **1段目**（hypeRate）と、大事件時の λ 一時上昇 |

`MarketHeat.Compute(priceHistory, halfLife, reference)` は**状態を持たず価格履歴だけで計算**でき、
`Describe()` が「凪 / 静か / 平常 / 活況 / 荒れ」を返す。**市況面の文言と相場欄の色にそのまま使う**（新規実装ほぼゼロ）。

## 8. 購読

| 項目 | 値 |
|---|---|
| 契約単位 | 5ターン |
| 購読枠 | **1 → 2 → 3**（3が上限。5社全購読は不可） |
| 枠の解放 | **店レベル**（周内で完結する。村メタでは増やさない） |
| 変更可能タイミング | 契約更新ターンのみ |
| 未購読時 | 無料の壁新聞が一面に1〜2本だけ出る（画面が空になるのを防ぐ） |
| 支払い | 契約開始時に一括。固定費として毎期のしかかる |

初期資金 100,000G に対し最高額の官報でも 20,000G なので、**購読料は序盤の制約にならない**。
**序盤のゲートは購読枠1枠**が担う。「金では買えるが、枠がない」が制限の本体。

参考値: 借金は7ターンごと 5,000G から ×1.8 の複利（`GameConstData.cs:19-21`）、アイテム単価 700〜1,000G。

## 9. スクラップと確認

### 9.1 状態遷移

```
[貼る] --> 保留(砂時計)      発効 + duration が経過するまで
       --> 決着・未確認(?)   価格の動きは見えるが真偽は不明
       --> 確認済み(○/×)     有料確認。社の実測的中率に積まれ、名鑑へ移動して枠が空く
```

| 項目 | 値 |
|---|---|
| 貼り方 | 記事本文を開いて「スクラップする」。**手動のみ** |
| 枠 | 初期3件。店レベル / 村メタで増加 |
| 枠が満杯 | 「スクラップする」を不活性化し、理由を表示する |
| 確認（個別） | 1,500G |
| 確認（まとめて） | 3件 4,000G |
| 枠の解放条件 | **確認すること**（確認済みは名鑑へ移動する） |
| 無料経路 | **訂正記事**。数ターン遅れてうわさ欄の隅に小さく出る |

確認は「真実を売る」のではなく「**時間と確実性を売る**」。払わなくても訂正記事で分かるので、学習が金で止まらない。

### 9.2 社の実測的中率

- **確認した記事だけ**が社の的中率カウンタに積まれる
- 左サイドバーの信頼バーは**公称値**。その下に細い**実測バー**を重ねて表示する
- 確認への支払いが「新聞社を見極める投資」になる。周を跨いで残せば村メタの報酬になる

### 9.3 貼った記事の参照

貼った記事は**仕入れ画面の端に付箋として出る**。
ただし**記事から銘柄へのジャンプリンクは作らない**。作った瞬間に「記事 = 銘柄」が機械的に判明し、推論という遊びが消える。紐付けはプレイヤーがやる。

### 10.3 面の扱い

- **面タブはその社が保有する面のみ表示**（`newspapers.tsv` の `pages`）。網羅バーと一致する
- 「自店」は新聞社に依存しないので**紙面の外**、下タブ列に常設・無料。現 `MorningReportModel` がそのまま入る
- ただし自店がバズって本当に記事になったときだけ、その社の一面に載る

### 10.4 UI 原則

- 記事は**見出し＋リード文を常時表示、本文はクリックで開く**。推論のヒントは本文に置き、読む人が得をする構造にする
- **訂正記事は本当に小さく隅に**置く。見落としは自己責任
- 縦書きは使わない（TMP の縦書きは実用に耐えない）。横書き2段組＋罫線＋題字＋写真枠で新聞らしさを出す
- 1号あたり 6〜8本、見出しだけなら20〜30秒で流せる分量に収める

## 13. Jev による検証（開発時のみ）

Jev は文章を生成せず、ランタイムでも呼ばない。**記事の品質検証と数値決定に使う。**

| # | 用途 | 質問型 | 判定 |
|---|---|---|---|
| J1 | **解読可能性**（最重要） | Choice（全銘柄から1つ） | 正解に確率が集中 = 解ける / 分散 = 因果が繋がっていない / 別銘柄に集中 = **ミスリード記事** |
| J2 | 誤報の見抜きやすさ | Score | 署名・面・`sourceClarity` だけを見せ、検出率が 60〜75% に入るか |
| J3 | 社の個性 | Choice（5社から） | 社名を伏せて当てさせる。当たらない社は文体が書き分けられていない |
| J4 | 効果量の一貫性 | Score | 100本の `trendDelta` に一貫した目盛りを引く |

J1〜J3 は日本語本文を読ませるため `summaryEn` 列が要る。J4 は出来事の構造情報だけで足りる。
1リクエストに複数質問を並列で詰められるため、100本でも数十円。
