# 配信フェーズ改修 企画書（Streaming Redesign）

作成: 2026-10-05 / 更新: 2026-10-05（§6 ユーザー決定を反映・P1 実装・実演販売不採用／介入3種の金額確定／視聴者スパチャは収入に含めない）/ 対象: FightScene（配信＝勇者のダンジョン戦闘＋その間の販売）

---

## 0. 背景と課題

チームで出た要望:

- 配信フェーズが**短すぎる**（Lv1 で戦闘本体 約8秒）。スピードを落としたい、ウェーブを伸ばしたい
- **プレイヤーが見るものがない**（ログ文字列は非表示。キャラは棒立ちでダメージ数字が出るだけ）
- 妖怪ウォッチのように、**半自動で戦い、プレイヤーが少しだけ干渉**する形にしたい
- **スパチャで指示**が入る。**赤スパは必殺技**
- 配信の**コメント欄をニコニコ式**に（勇者が映っている画面の上をコメントが流れる）

この企画書は、すぐ効く調整（§1・実装済み）、ニコニコ式コメント（§3・実装済み）、
大きな改修（§2・§4・§5）の設計をまとめる。§6 はユーザー決定の記録。

## 1. すぐ効く調整（実装済み・2026-10）

### 1-1. やったこと

| 項目 | 変更前 | 変更後 | 置き場所 |
|---|---|---|---|
| 全体スピード倍率 | 2.99（FightScene の BattleUIView シーン値） | **1.0** | `GameConst.battleTempo.speedMultiplier` |
| ログ1件の待ち | 0.5 / 2.99 ≒ 0.17秒 | **0.4秒** | `logSeconds` |
| 攻撃モーション | なし（棒立ち） | **踏み込み→戻り 0.35秒**（踏み込み切った瞬間にダメージ） | `attackMotionSeconds` / `attackLungeDistance` |
| ターン間の間 | なし | **0.4秒** | `turnIntervalSeconds` |
| 戦闘開始→敵出現 | なし | **1.0秒** | `battleStartSeconds` |
| ウェーブ間インターミッション | なし | **2.0秒**（ゲージが進む演出を見せる。販売ループは動き続ける） | `waveIntermissionSeconds` |
| 増援待ち | 500ms ハードコード | 0.5秒（設定化） | `reinforceDelaySeconds` |
| 撃破点滅 | 5回×0.15秒 ハードコード | 同値（設定化） | `deathBlinkCount` / `deathBlinkInterval` |
| 通常ウェーブ周回数 | 1 | **4**（§1-4。ユーザー決定「ウェーブ数を増やして伸ばす」） | `normalWaveRepeat`（`BattleWavePlan`） |
| 時間販売ループ間隔 | 15±3秒（シーン値） | **40±6秒** | `salesLoopIntervalSeconds` / `salesLoopRandomness` |

設定値はすべて `GameConstData.battleTempo`（`GameConstSettings.asset` のベイク値／`gameconst.json` でサーバー上書き可）。
BattleUIView の Inspector 値は `overrideTempoInInspector` を ON にしたときだけ使う（デバッグ用）。

### 1-2. 所要時間の目安（実測）

FightScene 単体再生・Lv1（通常2体→ボス1体）・「はい」押下〜決着（カウントダウン3秒込み）:

| | 戦闘本体 | ＋カウントダウン |
|---|---|---|
| テンポ調整前 | 約 **7.7秒** | 約10.7秒 |
| テンポ調整後（周回1） | 約 **18秒** | 約21秒 |
| **周回4（現行）** | 約 **46秒** | 約**49秒** |

通常ウェーブ1周あたり 約9.5秒（撃破2体＋インターミッション2秒）。
目標「1配信 45〜60秒」に対し Lv1 で約49秒。敵が硬い・数が多いレベルほど長くなる（上限の目安 60秒を超えるダンジョンの周回数などダンジョンデータは**プランナーが調整する**。§6 #11）。

### 1-3. 売上・精算を壊していない根拠

- **ターン数・勝敗はテンポでは変わらない**。変えたのは待ち時間と見た目だけ（ダメージ計算・行動順・フェーズ構成は不変）。
- **ターン販売（`ExecuteTurnSales`）の回数はターン数に比例**。ターン終了時の価格変動・需要変動・配信熱の減衰回数も同様。
- **時間販売ループ**は実時間で回るため、間隔を 15秒→40秒 に伸ばして回数を据え置いた。
- **精算ロジック（`BattleSceneStarter`）は未変更**。`StopSales()` → スナップショット → 純利益計算の順序はそのまま。
- `StopSales()` で**ターン販売も止まる**（`_salesActive`）。配信終了ボタン経由で戦闘ループが裏で回り続けても売上が積まれない。

### 1-4. ウェーブ数の増加（normalWaveRepeat = 4）

ボス以外のウェーブを4周してからボス（`BattleWavePlan.Expand`）。
**ウェーブを増やすと変わるもの**（テンポ調整と違い、ゲーム性に効く）:

| 項目 | 影響 | 対応 |
|---|---|---|
| 難易度 | 勇者は回復しないまま4倍の雑魚と戦う → 敗北（＝防衛報酬）が増える | プレイテストで勝率を確認。重すぎれば 3 に下げる（3 で Lv1 約40秒） |
| 撃破数 | 武器値上がり・配信熱・属性相性の価格変動イベントが約4倍 | 価格の振れ幅が大きすぎないか確認 |
| ターン販売 | ターン数比例で販売回数が増える（持ち込み在庫が上限なので青天井ではない） | 在庫切れ→補充ポップアップが増える想定 |
| クリア確率表示 | **`ClearProbabilityCalculator.BuildPhases` の戻り値を `BattleWavePlan.Expand(...)` に通す必要あり**（1行） | Hero/ 担当側で対応（未適用だと確率が実戦より高く出る） |
| 勇者の経験値・レベルアップ | 撃破数が増える | 別途対応 |

## 2. 全体像

### 2-1. 体験の芯

> 勇者は**勝手に戦う**。トム（プレイヤー＝配信者兼商人）は**お金を払って口を出す**。
> 口を出す先は**勇者側（スパチャ）にも、ダンジョン側（魔物へのスパチャ）にも**できる。
> 勝たせて武器を値上げするか、負けさせて防衛報酬と防具の買い場を取るか。**どちらに賭けるかが商人の腕**。

妖怪ウォッチの「オート戦闘＋たまに介入」を、
**「勝ち負け」ではなく「相場と配信の盛り上がり」に効く介入**として落とし込む。
勇者側・ダンジョン側の両方に介入できるので、旧 §6-1 の「勝たせると防衛報酬が減ってねじれる」問題は
**どちらに張るかの選択**に変わる（ねじれではなく戦略になる）。

## 3. ニコニコ式コメント（P1・実装済み）

### 3-1. 仕様

- 配信枠（勇者・敵が映る領域）の上を、コメントが**右→左へ等時間で流れる**（1コメ4秒で横断。長文ほど速い）
- コメントは**戦闘イベント駆動＋雑談**。ゲーム性への影響は**なし**（見た目のみ）
- 文言は**ニコニコ寄り**（わこつ・888・草・wktk・うぽつ 等。下品なものは入れない）
- 密度は**配信熱と同接**で変わる。雑談間隔 = Lerp(2.6秒, 0.45秒, 熱/100) ÷ 同接倍率
  - 同接倍率 = √(同接 / 150)、0.5〜2.5 にクランプ
  - 弾幕（撃破・ボス出現など）の件数にも同接倍率を掛ける（上限 1.6 倍。増えた分だけ散らす秒数も伸ばして読める量を保つ）
- 上下固定コメント（ue/shita）は「ボス出現」「完売御礼」などの強調用。**1イベント1件まで**、同じ文言は重ねない
- バズ状態で出る文言が変わる（「バズから来ました」「祭り会場はここですか」「なんか燃えてるらしい」等）
- ポーズ中は流れも止まる。配信終了で新規生成停止、予約済みの弾幕は流し切る
- コメントは入力を受けない（敵タップ・売り場ドラッグを邪魔しない）
- 表示量 ON / 少なめ / OFF（PlayerPrefs 保存）の API は実装済み。切替ボタンは未配置（§7 P5）

### 3-2. 同接表示（P1・実装済み）

- 配信枠の左上に **赤丸（ゆっくり明滅）＋人型アイコン＋人数**。人数は目標値へなめらかに近づき、少し揺れる
- 同接の目標 = (基礎60 + フォロワー×0.5) × バズ倍率（通常1.6 / 超バズ3.0 / 炎上1.4）× 配信熱倍率（熱0で0.6 〜 熱100で1.8）
- ボス出現 +15%・ボス撃破 +12%・敵撃破 +3% の瞬間流入
- **表示とコメント量にだけ使う**（売上・精算には影響しない）。調整値は `GameConst.streamingAudience`
- フォロワー数・バズ状態は `StreamingAudienceBridge` から読む。未設定ならフォロワー数をセーブ（shopStatusData.json）から読み、バズは「なし」扱い
  → 配信遷移時に GameFlowManager から `StreamingAudienceBridge.Set(...)` を呼ぶ配線は P4

### 3-3. 実装（クラス構成）

配置: `Assets/Scripts/Battle/Comments/`・`Assets/Scripts/Streaming/`

| クラス | 役割 |
|---|---|
| `StreamingCommentTypes`（enum / struct） | `StreamingCommentTrigger`・`NicoCommentSize`・`NicoCommentPosition`・`NicoDensity`・`StreamingCommentBuzzCondition`・`StreamingCommentRequest` |
| `StreamingCommentCatalog`（SO, Addressable `StreamingCommentCatalog`） | 文言（**CSV で差し替え**）・トリガー別の弾幕量・雑談間隔・同接→量の倍率・同時表示上限 |
| `StreamingCommentFeed`（Model） | イベント→文言抽選（重み・minHeat・buzz 条件・直前と同じ文言を避ける）→置換→弾幕の時間差予約。雑談ループ。`Push()` は将来のスパチャ・必殺技の差し込み口 |
| `NicoLaneAllocator` / `NicoFixedLaneAllocator` | 流れコメの衝突回避（追いつかない・尾が画面に入っている、の2条件）。置けるレーンが複数あればランダム |
| `NicoCommentLayerView`（View） | 配信枠を覆う RectMask2D 領域。プール・Update 一括移動・ポーズ・上限超過時は優先度の低い古いものから捨てる |
| `StreamingAudienceModel` / `StreamingAudienceBridge` | 同接の計算と、店側からの入力口 |
| `StreamingViewerCountView` | 同接表示（カウントアップ・大きく増えたら跳ねる・赤丸の明滅） |
| `StreamingCommentDirector`（Presenter） | 上記の配線。開始/終了は `StreamingSalesController.IsSalesActive` に揃える（BattleSceneStarter の変更なし） |

文言データ: `Assets/Resources_moved/Streaming/StreamingComments.csv`（162件・16トリガー）
列: `trigger,text,weight,size,position,color,minHeat,buzz`。置換 `{hero} {enemy} {item} {price} {viewers}`。
フォント: `MPLUSRounded1c-Bold SDFPlusPadding` ＋ 新規マテリアル `… SDFPlusPadding NicoComment.mat`（白文字＋黒縁）。

## 4. 介入（勇者側・ダンジョン側）と裏表フリップ画面

### 4-1. 介入の一覧

**支払いはすべてプレイヤーの所持金**。勇者側（表）は**赤・青・緑の3スパ（金額確定）**、ダンジョン側（裏）は**勇者側と対にせず独自の4種**（2026-10-05 決定）。

**勇者側（表）**

| スパ | 金額 | 効果 |
|---|---|---|
| **赤スパ** | **100,000G** | **必殺技**: カットイン＋大技（×3、対象1体）。熱 +20、装備中の武器の需要・価格UP（「その剣なに？」弾幕） |
| **青スパ** | **50,000G** | **スキル**: 次の攻撃をスキル攻撃（×1.5）。敵をタップして指定すれば狙う敵を変えられる（総ダメージは同じ）。熱 +10、装備中の武器の需要UP |
| **緑スパ** | **10,000G** | **回復**: 勇者 HP +30%。撃破が遅れる＝ターン数↑（販売機会↑） |

**ダンジョン側（裏）**（金額は**仮値・プレイテストで調整**）

| 介入 | 金額（仮） | 効果 |
|---|---|---|
| **増援を呼ぶ** | 50,000G | 魔物を1体追加（またはウェーブを1つ追加）。配信が延びて販売機会↑、勇者はやや不利 |
| **罠を仕掛ける** | 10,000G | 勇者が次に受ける攻撃に追加ダメージ（または状態異常）。防具の需要・値下がりに効く |
| **ボス強化** | 100,000G | この配信中だけボスのステータスを上げる。防衛報酬狙いの大きな賭け。**1配信1回まで** |
| **呪い** | 30,000G | 勇者の攻撃力（または命中）を一時的に下げる。勇者側の赤スパ（必殺技）への対抗手段 |

- ダンジョン側に魔物の必殺技・スキル・回復はない（旧案を削除）。旧「ターゲット指示（単独）」は青スパの対象指定に吸収。「増援を呼ぶ」は一度廃止したが**復活**
- **属性フィールド（ダンジョンの属性を変える）案は不採用**（ダンジョンごとの属性は既に決まっているため変えない）
- 効果量（×1.5・+30% 等）は仮値で `StreamingInteractionSettings` から調整する
- 初期資金はサーバー配信で 100,000G（参考）。赤スパ1発＝初期資金と同額なので、序盤は緑・青が中心で、赤は稼いでから張る賭けになる
- 戦闘への効果は「介入でちょっと上振れ／下振れ」程度に抑える。`ClearProbabilityCalculator` は**放置時の見込み**として表示する
- 数値（金額・倍率）はすべて新 SO `StreamingInteractionSettings`（Battle 系 SO。`BattlePriceSettings` と同じロード方式）
- 勇者側・ダンジョン側のどちらに払っても、**払った額は返らない**（ただし §5-3 の「未実行の指示」は返金）

### 4-2. 介入回数の上限（推奨案を採用）

| 上限 | 値 |
|---|---|
| 必殺技（勇者側の赤スパのみ。視聴者の赤スパ起点も含む） | **1配信 2回まで** |
| ボス強化（ダンジョン側） | **1配信 1回まで** |
| 同時に有効な指示（両面共通） | **1件**（実行されるまで次の指示は出せない。カードのボタンがグレーになる） |
| 指示を出した後のクールダウン（両面共通） | 6秒（調整値） |

売り場のドラッグ・補充と両立させるため、介入は「たまに1タップ」の頻度に収める。

### 4-3. 裏表フリップ画面（介入カード）

配信枠の右上パネル（旧ログウィンドウ）を**1枚のカード**にし、表と裏で面を切り替える。

| 面 | 中身 |
|---|---|
| **表: チャット欄＋勇者側** | 上: チャット欄（スパチャのカードが下から積み上がる。視聴者スパチャ・自分のスパチャとも色付き）／下: 勇者側の介入ボタン3つ（緑=回復・青=スキル・赤=必殺技）。文字は金額のみ |
| **裏: ダンジョン側** | 上: 前列の魔物の顔アイコンと HP 小バー（ボスがいれば強調）／下: ダンジョン側の介入ボタン4つ（増援・罠・ボス強化・呪い。金額表示）。紫〜暗赤の配色で表と見分ける |

**遷移（カードをめくる）**:
1. カード右上の「めくり」タブ（勇者アイコン⇔魔物アイコン。文字なし）をタップ、またはカード面の空き部分をスワイプ
2. DOTween: `localRotation.y` 0→90°（0.14秒, InQuad）→ 面を差し替え → 90→0°（0.18秒, OutBack）＋ 1.04 倍のポップ。`SetLink(gameObject)`
3. めくり中（約0.3秒）は入力を受けない。**戦闘は止めない**（操作のたびに止まるとテンポが死ぬ）
4. 表で新しいスパチャが届いたとき、裏を見ていればタブが小さく跳ねて知らせる（自動ではめくらない）
5. 配信開始時は表。最後に見ていた面はその配信中だけ保持（保存しない）

裏表で操作対象が完全に分かれるので、誤タップで逆側に払う事故が起きにくい。

### 4-4. 実装構造

```
InterventionCardView (MB)          … 裏表2面・めくりアニメ・ボタン状態（グレー/クールダウン）
InterventionPresenter               … ボタン→支払い→指示キューへ。上限・クールダウン管理
InterventionCommandQueue (plain C#) … 1件だけ保持。勇者/魔物の手番で消費
   ├ SpecialMoveCommand                ← 赤スパ（勇者の必殺技）/ 視聴者の赤スパ（演出）
   ├ SkillCommand(target?)             ← 青スパ（敵タップで対象指定可）
   ├ HealCommand                       ← 緑スパ（勇者の回復）
   ├ ReinforceCommand                  ← 増援（現在フェーズのキューに魔物1体、またはウェーブ追加）
   ├ TrapCommand / CurseCommand        ← 罠（勇者の次の被弾に追加）/ 呪い（勇者の攻撃力を一時ダウン）
   ├ BossBuffCommand                   ← ボス強化（その配信中のみ。1配信1回）
StreamingInteractionSettings (SO)   … 各介入の金額・倍率・上限・クールダウン
SpecialMoveCutInView (MB)           … 勇者立ち絵＋赤帯
```

- `BattleActionExecutor.ExecuteTurnActionsAsync` の各手番でキューを消費（勇者側の指示は勇者の手番、ダンジョン側の指示は即時／魔物の手番で反映）
- 増援は `BattleContext` の現在フェーズのキューに足す（`SpawnFromPhaseQueueAsync` が既存の流れで出す）
- `GetAttackTarget(hero)` は `context.SelectedTarget`（青スパで指定）が生存していればそれを返す
- ダメージ倍率は `CharacterPresenter.PerformAttack` に引数を足す（`OnCharacterDamaged` はそのまま発火＝価格変動・熱は既存経路で動く）

## 5. スパチャ（プレイヤー払い＋視聴者ランダム）と赤スパ必殺技

### 5-1. 2種類のスパチャ

| | プレイヤー払いスパチャ | 視聴者スパチャ（ランダム） |
|---|---|---|
| 発生 | 介入カード（表・裏）のボタン | 同接と配信熱に応じてランダム |
| お金 | **所持金から支出**（介入支出） | **プレイヤーの収入に含めない**（演出・盛り上がり・同接への効果のみ。2026-10-05 決定） |
| 指示 | 必ず実行される（§4-1） | 「ボス倒して！」等の**お願い**がつくことがある。期限内に起きれば熱 +5（操作不要） |
| 赤スパ | 勇者の必殺技 | **勇者の必殺技が自動で出る**（必殺技の上限 2回に含む。上限後は大弾幕＋熱UPのみ） |
| 表示 | チャット欄にカード＋流れコメに同色の上固定コメ | 同左 |

- 色は YouTube 準拠（青/水/緑/黄/橙/桃/赤）。プレイヤー払いは3種（緑 10,000G・青 50,000G・赤 100,000G）に絞る
- 視聴者スパチャの発生率: 1分あたりの期待件数 = 同接 / 100 × (0.5 + 熱/100)。色の重みは同接が多いほど赤寄り（超バズ中は赤スパ率UP）。金額は**表示上のみ**で所持金・精算には反映しない
- 視聴者スパチャは同接・熱を押し上げる（受信時に熱 +、同接へ瞬間流入。調整値は `GameConst.streamingAudience` 側）
- 視聴者スパチャのコメントは `StreamingCommentFeed.Push(SuperChat…)` で差し込む（トリガー追加で文言は CSV）

### 5-2. 必殺技（スパチャ起点）

- **必殺技は赤スパに反応して出る**（自前のゲージは持たない）
- 赤スパ → 勇者の次の手番で発動: カットイン（勇者立ち絵 `勇者_10_真剣` 等＋赤帯）→ 大技（×3）→「うおおおお」弾幕
- ミニゲーム（タイミング円で倍率 0.5〜1.5）は**入れない**。忙しさ対策。演出の作り込み段階（P5）で再検討

### 5-3. 精算への組み込み（重要）

**お金の流れ**:

```
純利益 = 売上 − 補充費用 + 売れ残り補充分の返金 + 敗北時報酬
       − 介入支出（緑・青・赤スパ）+ 未実行の介入の返金
```

- 視聴者スパチャは**式に含めない**（収入にしない）
- 介入支出は**払った瞬間に** `_interventionSpending` に積む（補充の `_battleSpending` と同じ扱い。PlayerMoney は戦闘終了時に一括精算）
- 支払いの可否は補充と同じ「利用可能残高」= 所持金 + 戦闘中売上 − 補充費用 − 介入支出

**停止とスナップショットの順序**（既存の「止めてから集計」の原則を守る）:

1. 決着（または配信終了ボタン）→ `_pauseController.Resume()` → `battleCts.Cancel()`
2. **`InterventionPresenter.Stop()`**: 新しい支払いを受け付けない。キューに残った**未実行の指示は返金**（決着で効果が出なかったため）
3. **`SuperChatGenerator.Stop()`**: 視聴者スパチャの演出発生を止める
4. `_salesController.StopSales()`
5. **ここでスナップショット**（売上・補充・介入支出・返金をまとめて確定）
6. 純利益を計算 → `BattleOutputData.SetResult(...)`

- `BattleOutputData` に `InterventionSpending` / `PeakViewers` を追加（SceneData/ の担当と調整）
- リザルト画面（`BattleResultView`）に「介入」の1行を追加
- 介入で所持金がマイナスにならないこと（ボタンは残高不足でグレー）

### 5-4. Marketing（バズ・フォロワー）との接続

| 方向 | 内容 | 変更箇所 |
|---|---|---|
| Shop → Fight | 配信開始時のフォロワー数・バズ状態 → 同接の初期値・コメントの出し分け | GameFlowManager の配信遷移で `StreamingAudienceBridge.Set(followers, isBuzz, buzzType)`（受け口は P1 で実装済み） |
| Fight → Shop | 配信で増えたフォロワー（最大同接・視聴者スパチャ件数・必殺技から算出） | `BattleOutputData.FollowerGain` を追加し、`BattleResultHandler` で `ShopStatusModel` に加算 |
| バズ演出 | 超バズ中は赤スパ率UP・コメントに虹色を混ぜる | `StreamingCommentCatalog` の buzz 列（実装済み）＋ SuperChatSettings |

### 6-1. 未決（残り）

1. **介入の効果量**: 青スパの倍率（仮 ×1.5）・緑スパの回復量（仮 +30%）・赤スパの大技倍率（×3）、およびダンジョン側4種の金額と効果量（罠の追加ダメージ・ボス強化の上昇率・呪いの下げ幅・増援が魔物1体かウェーブ1つか）は仮値。プレイテストで `StreamingInteractionSettings` を調整
