## 0. なぜ作り直すか（現状の問題）

| 症状 | 原因 |
|---|---|
| 購読した社の紙面が空の日がある | 記事21本を **1ターン3本だけ** 抽選し、全5社へ散らしている。社ごとに号を作っていない |
| クロスリファレンスが成立しない | `crossRefGroup` 列はあるが、スケジューラが使っていない。同じ事象を別の社が書いた記事が無い |
| 社の個性が出ない | 文体は記事ごとに手書き。社が変わっても同じ文章が載る |
| 誤報率 `falseRate` が効いていない | 誤報は記事の `truth` 列で固定されている |

**方針（ユーザー決定 2026-10-08）**

1. 記事は「**事象**」1つから、**社ごとの文体テンプレート**で最大5本に展開する。1事象を複数社が報じるので、クロスリファレンスが自然に成立する
2. 1号の本数を **各社1〜3本** に減らす（例: 王立1・ギルド3・商業2・かわら版3・職人1）
3. **効果のない埋め草**（天気・祭り・村の話題など）で号を埋め、紙面が空にならないようにする
4. 文章は **AI が下書き → ユーザー/プランナーが CSV で確認・修正**。Jev で「記事から正解の銘柄が推理できるか」を検証する

## 1. 用語（追加分）

| 用語 | 定義 |
|---|---|
| 事象（event） | 世界で起きる出来事1つ。**効果（対象・規模・真偽）はここが持つ**。例: 火山の噴火、勇者の昇格 |
| 事象パターン | 事象の雛形。差し込み枠（ダンジョン名・属性など）を持ち、周ごとに具体化される |
| テンプレート | 事象パターンを、ある1社の文体で記事にした文面（見出し・リード・本文）。報道／結果／訂正の3種 |
| 報道（report） | 事象を1社が1回報じた掲載。**効果を持たない**（効果は事象側） |
| 埋め草（filler） | 効果を持たない記事。天気・祭り・村の話題など。号の本数を満たすために使う |
| 発効ターン | 事象の効果（2段目）が来るターン。**事象ごとに1つ**。各社はここから自社の lead だけ前に報じる |

## 2. データ構造（§4.2・§4.3 を置き換え）

マスターは3枚＋既存の新聞社マスター。区切りはタブ、拡張子は `.csv`（Unity が `.tsv` を TextAsset として取り込まないため。現行と同じ）。

### 2.1 `Newspapers.csv`（新聞社・5行）— **変更: 列を追加**

既存の11列は残す。`articlesPerIssue` の意味を「1号の本数」に変える。

| 追加列 | 型 | 説明 | 初期値の例 |
|---|---|---|---|
| issueMin / issueMax | int | 1号の本数の幅（`articlesPerIssue` は廃止して置き換え） | 王立 1/1・ギルド 2/3・商業 2/2・かわら版 2/3・職人 1/1 |
| pageSlots | string | 面ごとの上限 `front:1,second:1,market:1` | §4 参照 |
| bylines | string | 記者名の候補（`|` 区切り）。空 = 社の部署名で出す | 王立 `王立広報局`／かわら版は空が多い |
| bylineRate | float | 署名が付く確率（残りは無署名） | 王立1.0・ギルド0.9・商業0.8・かわら版0.3・職人0.9 |
| clarityWeights | string | sourceClarity の出やすさ `confirmed:0.8,presumed:0.2,anonymous:0` | §2.5 参照 |
| reportRate | float | 自社のカテゴリの事象を報じる確率 | 王立0.6・ギルド0.9・商業0.8・かわら版0.7・職人0.8 |
| styleNote | string | 文体メモ（AI 下書きへの指示に使う。製品には出さない） | 王立「硬い公文書調」 |

`falseRate` は「その社が**誤報の事象**を拾う重み」として使う（§3.3）。`categories` と `pages` はそのまま使う。

### 2.2 `NewsEvents.csv`（事象パターン）— **新設**

1行 = 1パターン。**効果・真偽・続報の有無はここだけが持つ**。

| 列 | 型 | 説明 |
|---|---|---|
| eventId | string | `EV_VOLCANO` など |
| category | string | `dungeon` / `hero` / `rival` / `supply` / `culture` / `economy` / `village`（`correction` と `shop` は廃止 → §2.6） |
| scale | string | `small` / `medium` / `large`。効果量は `NewsTuning` の目盛り（小0.3・中0.6・大1.0）から引く |
| sign | int | `+1`（売れる）/ `-1`（売れなくなる） |
| targetRule | string | 対象の決め方。`L1:{dungeon}`（そのダンジョンの弱点属性の武器）/ `L2:{dungeon}`（その攻撃を防ぐ属性の防具）/ `L3`（高額帯）/ `attr:Fire,Weapon`（固定）/ 空 = 効果なし |
| binds | string | 差し込み枠と、その決め方。`dungeon=next`（次のダンジョン）/ `dungeon=any` / `region=pool` など |
| truthWeights | string | 周で具体化するときの真偽の出やすさ `true:0.75,exaggerated:0.15,false:0.10` |
| hasResult | bool | 決着時に結果記事を出すか |
| condition | string | 出現条件（既存と同じ書式。`nextDungeon=IceCave` / `heroLevel>=3` / `shopLevel>=2` / `turn>=5`） |
| weight | int | 抽選重み |
| cooldown | int | 同じパターンを再び置くまでの最短ターン数（既定 10） |
| summaryEn | string | Jev 用の英語1行要約。差し込み枠はそのまま `{dungeon}` で書く |
| family | string | 系統（2026-10-08 追加・最終列）。**cooldown はこの単位で効く**。次ダンジョン別に分割した事象（`EV_HERO_EXPEDITION_VOLCANO` など）は分割前の ID を入れる。空 = eventId |

**L2 の対応表**（敵の属性 → それを防ぐ防具の属性）は `items_sheet.tsv` の説明文から1回だけ抜き出し、
`NewsTuning` か別 CSV に持つ（§12 未決 U4）。

### 2.3 `NewsTemplates.csv`（社別テンプレート）— **新設**

1行 = 1社 × 1パターン × 1種類。

| 列 | 型 | 説明 |
|---|---|---|
| templateId | string | `EV_VOLCANO.guild.report` |
| eventId | string | 対応する事象パターン |
| companyId | string | `royal` / `guild` / `commerce` / `tabloid` / `craft` |
| kind | string | `report` / `result` / `correction` |
| tone | string | `normal` / `loud`（誇張・誤報で使う煽り版。無ければ normal を使う） |
| page | string | 載せる面の希望。空 = §4 の規則で決める |
| headline / lead / body | string | 文面。差し込み枠 `{dungeon}` `{region}` `{monster}` `{hero}` などを使える。**効果・数値・銘柄名は書かない**（D1） |
| clarity | string | 空 = 社の `clarityWeights` から抽選。書けば固定 |
| status | string | `draft` / `reviewed` / `approved`（§7） |
| reviewNote | string | 確認者のメモ。製品には出さない |
| summaryEn | string | Jev 用 |

- 1パターンにつき、**その事象のカテゴリを扱う社の数だけ** report を用意する（2〜4本）
- result は報じうる社ごとに1本（社の文体で「その後」を書く）。correction は誤報を拾いうる社ごとに1本
- テンプレートが無い社は、その事象を報じない（＝テンプレートの有無が「どの社が報じうるか」を決める）

### 2.4 `NewsFillers.csv`（埋め草）— **新設**

| 列 | 型 | 説明 |
|---|---|---|
| fillerId | string | `FL_WEATHER_01` |
| topic | string | `weather` / `festival` / `village` / `people` / `notice` など |
| companies | string | 載せうる社（カンマ区切り）。空 = 全社 |
| page | string | 載せる面。`front` には原則置かない（§4） |
| headline / lead / body | string | 差し込み枠を使える（`{season}` `{village}` など） |
| cooldown | int | 同じ社で再び載せるまでの最短ターン数（既定 8） |
| weight | int | 抽選重み |
| status / reviewNote / summaryEn | | §2.3 と同じ |

**埋め草の禁止事項**: 属性・武器・防具・ダンジョンを連想させる語を書かない（推理のノイズではなく、
**ミスリード**になってしまう）。Jev J1 で「対象なし」に寄らない埋め草は不合格（§8）。

### 2.5 sourceClarity と署名の決め方

**事象の真偽ではなく社が決める**のを基本にし、誤報のときだけ半段ずらす。こうすると「無署名だから誤報」と機械的に読めず、
「この社でこの書き方は珍しい」という読みになる。

| 社 | 署名率 | clarity（confirmed / presumed / anonymous） | 誤報のとき |
|---|---|---|---|
| 王立官報 | 1.0（部署名） | 1.0 / 0 / 0 | 誤報を拾わない（falseRate 0） |
| 冒険者ギルド報 | 0.9 | 0.6 / 0.4 / 0 | presumed 寄り |
| 週刊商業新聞 | 0.8 | 0.4 / 0.5 / 0.1 | presumed か anonymous |
| 街角かわら版 | 0.3 | 0.05 / 0.35 / 0.6 | anonymous 寄り（ただし本物でも anonymous が多い） |
| 職人季報 | 0.9 | 0.7 / 0.3 / 0 | presumed 寄り |

- 署名は社の `bylines` から**事象ごとに固定**で選ぶ（同じ事象の続報は同じ記者が書く）
- sourceClarity は紙面に文字で出さない。リード文の言い回し（「〜を確認」「〜とみられる」「〜という話だ」）として
  テンプレート側に書き分ける。`clarity` 列はその言い回しを選ぶキーとして使う（§12 未決 U3）

### 2.6 真偽・誇張・続報の扱い

| 真偽（事象ごとに周で1回決める） | 報じる社 | 効果（2段目） | 続報 |
|---|---|---|---|
| true | `reportRate` に従い複数社（1〜4社） | 満額 | 決着ターンに、報じた各社が結果記事 |
| exaggerated | 複数社。うち1社以上が `tone=loud` | `× ExaggeratedScale`（0.5） | 結果記事（「噂ほどではなかった」） |
| false | **1社だけ**（`falseRate` を重みに選ぶ。王立は選ばれない） | なし | 決着 + `CorrectionDelay` に、**誤った社自身**が訂正記事 |

- 「1紙しか報じていない記事は怪しい」が成り立つように、**本物でも1社だけが報じる事象**を一定割合（目安25%）混ぜる。
  1社＝誤報、と決め打ちできないようにするため
- カテゴリ `correction` は廃止し、`NewsTemplates.csv` の `kind=correction` に移す。訂正は従来どおり「お詫びと訂正」枠へ
- カテゴリ `shop`（自店欄）は新聞社に依存しないので、フェーズ3の対象外（自店面は `MorningReportModel`）

### 2.7 既存 `NewsArticles.csv` からの移行

| 既存 | 移行先 |
|---|---|
| N001〜N013（通常記事） | 同じ `crossRefGroup` ごとに1事象パターンへまとめる。`targetAttribute/Type`・`trendDelta` → `targetRule`・`scale`・`sign`。`truth` → `truthWeights` の初期値 |
| 本文（headline/lead/body） | 元の記事を書いた社（`page` と文体から推定）のテンプレートとして残し、他社分を AI 下書きで足す |
| R001〜R013（結果記事） | `kind=result` のテンプレート |
| C007〜C012（訂正記事） | `kind=correction` のテンプレート |
| byline / sourceClarity | 社の `bylines` / `clarityWeights` へ吸収。記事ごとの指定はテンプレートの `clarity` 列で残せる |

移行後、`NewsArticles.csv` は読み込まない（`NewsMasterLoader` は新3枚を読む）。旧 CSV はファイルとして残して比較できるようにする。

## 3. 発行カレンダーの生成（§6.1 を置き換え）

**入力**: 周のシード（`FlowSeed`）、`GameFlow` のノード列（戦闘の位置とダンジョン）、マスター。
**出力**: 事象の一覧（発効ターン・真偽・具体化された差し込み枠）と、各社の号（ターン × 社 → 記事の並び）。
購読とは無関係に**全社分**を作る。シードだけ保存すれば再現できる（現行と同じ）。

### 3.1 手順

1. **事象を置く**: ターン2〜(最終−1) の各ターンについて、そのターンに**発効する**事象を0〜2件置く
   - 条件（`condition`）を満たし、`cooldown` が明けたパターンから `weight` で抽選
   - 差し込み枠を具体化する（`dungeon=next` なら、そのターンから見た次の戦闘のダンジョン）
   - 真偽を `truthWeights` で決める
2. **報じる社と日を決める**: その事象のテンプレートがある社ごとに `reportRate` で報じるか決める（誤報は1社だけ、§2.6）。
   報じる日は **発効ターン − その社の lead**（王立1・ギルド2・商業2・かわら版3・職人1）。ターン1より前になる社は報じない
   → 同じ事象を、かわら版が3日前・ギルドが2日前・王立が前日に報じる＝**時間差クロスリファレンス**
3. **続報を置く**: 決着ターン（発効 + duration）に結果記事、誤報は決着 + `CorrectionDelay` に訂正記事。乱数は使わない
4. **号を埋める**: 社ごと・ターンごとに、報道と続報を並べ、本数が `issueMin` に届かなければ埋め草で補う。
   `issueMax` を超えたら、規模の小さい事象の報道から翌日へ送る（送れなければ落とす。落とした報道は効果に影響しない）
5. **面を割り当てる**（§4）

### 3.2 保証

| 項目 | 内容 | 現行（§6.1）との違い |
|---|---|---|
| 大事件 | 1周に `large` を2回以上（Short は1回以上） | 同じ |
| トレンドの波 | 同じ属性に効く事象が、3〜5ターンの間隔で2本以上続く波を1周に3回 | 同じ |
| 誤報 | 1周の誤報の数 ≒ 報道数 × 各社 falseRate の平均（王立は0） | 社の falseRate が初めて効く |
| 空の号 | **どの社も、どのターンも1本以上**（埋め草で保証） | 新設 |
| 埋め草の再登場 | 同じ社で `cooldown`（既定8ターン）以内に同じ埋め草を出さない。足りなければ別の社用の埋め草を借りる | 新設 |
| 事象の再登場 | 同じパターンは `cooldown`（既定10）以内に置かない。同じ具体化（パターン＋同じダンジョン）は1周に1回 | 新設 |

### 3.3 効果の扱い — **変更: 効果は事象に1回だけ**

- `NewsModel.ActiveEffectsOn` / `JustTriggeredOn` は**報道ではなく事象**を数える。
  同じ事象を3社が報じても、2段目（trendDelta / demandKick）は1回だけ
- 1段目（跳ね・hypeRate）は「皆が紙面を読んで飛びつく」ものなので**報道の日ごと**に起きる。
  ただし同じ事象の跳ねは**1日につき1回**（その日の報道のうち一番大きい面の値）。既存の上限 `HypeMax=1.12` もそのまま
  → 早い社が報じた日に小さく跳ね、遅い社（一面の大見出し）が報じた日にもう一度跳ねる＝「遅く知るほど高く買わされる」
- 跳ねの剥がれ（発効ターンから `HypeUnwindTurns`）は事象の発効ターン基準
- 効果量はすべて `NewsTuning` の目盛り（`scale` → 小0.3/中0.6/大1.0、kick と duration も同表）。記事ごとの個別値は持たない
- `NewsEffectResolver` の公開 API（`TrendBias` / `DemandKick` / `HypeRate`）は変えない。`ItemModel` 側の変更は不要

**副作用**: カレンダーの中身が変わるので、AutoPlay の収支は現行と一致しなくなる。
フェーズ3を入れたら AutoPlay（ニュース有り）を回し直し、`Docs/Level_Design_Log.md` に追記する。

### 3.4 スクラップ・確認との関係

- スクラップは従来どおり**報道1件**を貼る。真偽・決着は**その報道の事象**で判定する
- 社の実測的中率は「その社が報じた事象の真偽」で積む（誤報を拾った社だけが外れを積む）

## 4. 1号の本数と面の割り当て

| 社 | 1号の本数 | 面（pages） | 面ごとの上限 | 主に載るもの |
|---|---|---|---|---|
| 王立官報 | 1 | front | front:1 | economy・dungeon の公式発表 |
| 冒険者ギルド報 | 2〜3 | front, second, market | front:1, second:1, market:1 | dungeon・hero・rival |
| 週刊商業新聞 | 2 | front, market | front:1, market:1 | rival・supply・economy |
| 街角かわら版 | 2〜3 | front, rumor | front:1, rumor:2 | culture・hero・誤報 |
| 職人季報 | 1 | front | front:1 | supply |

3社購読で1ターン最大9本（例: ギルド3＋商業2＋かわら版3＋…）。読む量は増えても、効果を持つ事象は1ターン2〜3件のまま。

**面の決め方**（上から順に適用）

1. テンプレートの `page` が書いてあり、その社が持つ面ならそこ
2. 一面: その日の報道のうち規模が一番大きいもの（`large` > `medium` > `small`、同じなら発効が近い方）
3. カテゴリで決める: dungeon・hero → second / rival・supply・economy → market / culture・village → rumor。
   その社が持たない面なら front
4. 面が上限を超えたら次の候補の面へ。どこにも入らなければ翌日へ送る（§3.1-4）
5. 埋め草は一面以外の空き面へ。一面しか持たない社（王立・職人）は、報道が無い日だけ一面に埋め草を置く
6. 訂正記事は面に関係なく「お詫びと訂正」枠（現行どおり）

## 5. 必要数の見積もり

### 5.1 1周で消費する量（Long 30ターンの場合）

| 項目 | 見積もり | 根拠 |
|---|---|---|
| 置く事象 | 約30件（1ターン約1件） | 効いている事象が常時2〜3件 ÷ 持続（lead + duration ≒ 5〜7）＋誤報・効果なし事象 |
| 報道 | 約75本 | 1事象あたり平均2.5社 |
| 結果・訂正 | 約30本 | 1事象あたり報じた社ぶん（結果は複数社が書く） |
| 号の枠 | 300枠 | 全社合計10本/ターン × 30 |
| 埋め草 | 約200枠 | 300 − 報道 − 続報 |

### 5.2 枯れないための必要数

| 種類 | 必要数 | 考え方 |
|---|---|---|
| 事象パターン | **24以上** | cooldown 10 で30件を置くには、常に14以上が条件を満たして抽選可能であること。条件で絞られるぶんを見込んで24 |
| テンプレート（報道） | パターン × 平均3社 ≒ **72** | 社ごとの文体で書き分ける |
| テンプレート（結果） | ≒ **72**（報道と同数）。最小版は社ごとの共通文1本で代用可（§9 段階A） | |
| テンプレート（訂正） | 誤報を拾いうるパターン × 平均2社 ≒ **20** | |
| 埋め草 | **60以上** | 社ごとに cooldown 8 で、1ターン最大2本 → 8ターンで16種が要る社（ギルド・かわら版）がある。社の重なりを見込んで60 |

差し込み枠（ダンジョン6種・地名・季節など）で同じ文面でも具体化が変わるので、文面の数より体感の重複は少ない。

### 5.3 最初に用意する本数（推奨）

| 段階 | 事象 | 報道テンプレート | 結果/訂正 | 埋め草 |
|---|---|---|---|---|

## 6. 経済への影響のまとめ

- 効果は**事象ごとに1回**（§3.3）。社が増えても効果は増えない
- 効果量は `NewsTuning` の目盛りのみ。`scale` 列が小/中/大を選ぶ。記事ごとの `trendDelta` 等の個別指定は廃止

## 7. AI 下書き → 確認のワークフロー

1. **AI 下書き**（開発時のみ・ランタイムでは呼ばない）

## 14. J2（誤報の見抜きやすさ）不合格への対応（2026-10-08）

Jev J2 が検出率 82%（目標 60〜75%）・本物の誤検出 33% で不合格。誤報の58%がかわら版に集中し、
「かわら版＝誤報」と社で決め打ちされていた（ギルドの誤報は1本も見抜けていない）。
**手がかりを「社」から「記事の載り方」へ移す**。§2.5・§2.6 をこの節で上書きする。

| 変更 | 内容 |
|---|---|
| 誤報率（Newspapers.csv `falseRate`） | 王立 0 / ギルド 0.05→**0.12** / 商業 0.10→**0.15** / かわら版 0.35→**0.22** / 職人 0.05→**0.10**。誤報の事象数は `truthWeights` で決まるので変わらない（変わるのは「どの社が拾うか」だけ） |
| かわら版の署名 | 記者名を追加（ジャック・ピーター / ノラ・ベル）、署名率 0.3→**0.6**。本物のかわら版記事が一律に疑われないように |
| 同報なし | 本物でも**1社だけが報じる事象を 25%**（`NewsTuning.TrueSingleReportRate`）。残りの本物は**最低2社**が報じる。誤報は従来どおり1社だけ |
| 無署名 | 誤報の報道は署名率 × **0.5**（`FalseReportBylineFactor`）。本物は社の署名率どおり |
| 載る面 | 誤報の **60%**（`FalseReportHideRate`）は一面以外（うわさ欄 → カテゴリの面）へ回す。残り40%は本物と同じく一面。本物はその日の最初の1本を一面に置く（かわら版の本物も一面に載る） |
| 跳ね（経済） | 誤報が目立たない面に載っても、跳ねは**一面並み**で計算する（噂は広まる）。高値掴みの大きさを変えないため |

**実測**（Long 30ターン × 40シード、`Temp` の検証スクリプト）

| 指標 | 変更前 | 変更後 |
|---|---|---|
| 誤報のうちかわら版の割合 | 53% | 45% |
| 各社の報道に占める誤報 | かわら版12%・商業6%・ギルド3%・職人2% | かわら版11%・商業7%・ギルド5%・職人4% |
| 署名あり（誤報 / 本物） | 64% / 82% | 38% / 83% |
| 一面に載る（誤報 / 本物） | 89% / 91% | 42% / 92% |
| うわさ欄（誤報 / 本物） | 3% / 3% | 25% / 3% |
| 1社だけが報じた事象（本物） | 17% | 27% |
| 本物のかわら版記事の署名 / 一面 | 63% / 88% | 68% / 90% |

## 16. 難易度とレア（2026-10-09）

`NewsEvents.csv` の末尾に2列（記事担当が追加）。列が無い・空なら easy / common。

| 列 | 値 | 意味 |
|---|---|---|
| difficulty | easy / normal / hard | 記事から効き先を推理する難しさ |
| rarity | common / rare | レア＝「ぶっ飛んだ内容」（ドラゴンが店に来る等）。効き先は普通〜大きめ・予測しにくくてよい |

**発行カレンダーでの選び方**（`NewsCalendarBuilder.ChooseTier`）

1. **レア（別枠）**: 1件選ぶごとに 5%（`NewsTuning.RareEventRate`）ずつ「貯金」し、レアが出せるとき貯金の確率で出す。cooldown で出せなかった分は持ち越すので、周全体で 5% に近づく。Long 30ターン（事象≒30件）で1〜2件、Short では出ない周もある
2. **難易度**: 目標 易しい65% / 普通25% / 難しい10%（`DifficultyEasyShare` など）。**その周でいちばん目標に足りていない層**から選ぶ（少し揺らぎを入れる）。層に候補が無いとき（cooldown・条件）は候補のある層だけで選ぶ
3. 層の中は従来どおり `weight` で抽選。乱数はすべてシードから引くので再現できる

**レアの報じ方**: 報じうる社（テンプレートがある社）が**すべて**報じる（同報なしの25%ルールの対象外）。誤報になった場合は従来どおり1社だけ。
**規模 `huge`**（レア用）: `scale=huge` を書ける。trendDelta は合計が ±1 にクランプされるので「大」と同じ 1.0、直撃（demandKick 0.15）と持続（5ターン）を大きくする（`TrendHuge` / `KickHuge` / `DurationHuge`）。

**注意**: 難易度の構成は「選べる候補の層」に左右される。易しい層の系統（family）が少ないと cooldown で易しい層が空き、目標より普通・難しいに寄る。

## 17. 連載（ストーリーアーク。2026-10-09）

「60 Seconds!」のように数日にわたって記事が続き、結末が分岐する。全事象の15〜20%を連載にする。

**列**（`NewsEvents.csv` の末尾、difficulty・rarity の後。記事担当が追加）

| 列 | 内容 |
|---|---|
| arcId | 連載ID。単発は空 |
| arcStep | 1, 2, 3 … |
| arcNext | 次の話の候補 `条件:事象ID|条件:事象ID`。最終話は空。条件は `rand`（シード固定の抽選）/ `always` / `heroWin` / `heroLose`（直近の配信の勝敗）/ `hasStock` / `noStock`（前の話の効き先の商品を在庫に持つか） |

**配置**（カレンダー生成時）

- 連載の事象（第1話を含む）は通常の抽選に混ぜない。第1話は「同時進行2本未満」かつ「その周の連載の割合が目標 17.5% 未満」のとき 50% の確率で置く（`ArcMaxConcurrent` / `ArcShareTarget` / `ArcStartChance`）
- 次の話は**予約枠**（`NewsArcSlot`）だけ置く。前の話の発効から 1〜3ターン後（`ArcGapMax`）が**分岐の決定ターン**、そこから最大 lead（3）後が次の話の発効ターン。いちばん早い社（かわら版）は決定ターンの朝に報じる
- 分岐が `rand` / `always` だけなら、生成時にシードで決めて続きを置く
- 続きの話は前の話の差し込み枠（ダンジョン・地名）を引き継ぐ。各話は報じうる社が報じる（同報・誤報のルールは事象に従う）

**分岐の決め方**（`NewsCalendarBuilder.ChooseArcBranch`）: 状態の条件（heroWin / heroLose / hasStock / noStock）に合うものを並び順で優先 → 無ければ `rand` の中からシード抽選 → `always` → 候補全体からシード抽選（まだ配信していない等で状態の条件が決まらないとき、先頭に偏らないように）。

**ゲーム中の確定**（`NewsModel.ResolveArcs(turn, hasStock)`）

- `GameFlowManager.NextTurn` が日送りのたびに、**経済計算より前**に呼ぶ（決定ターンを迎えた枠を確定し、紙面へ差し込む）。朝刊の Presenter も開いたときに取りこぼしを確定する
- 直近の配信の勝敗は `RunHistory` の勝敗累計の増え方から判定（`ObserveStreamTotals`）。在庫は `ItemModel` の Stock
- 差し込むときに号が上限を超える分は、その号の埋め草を外す
- 確定した分岐は `newsArcs.json`（`SaveSlotManager.GetPath`・周のシード付き）に保存。カレンダーを組み直すと決定ターン順に当て直すので、**ロード後も同じ紙面**になる（検証: 20周で不一致 0）。新規ランでは `RunSaveCleaner` が消す

**AutoPlay 用の API**: `GameFlowManager.NextTurn` が自動で `ResolveArcs` を呼ぶので追加の呼び出しは不要。配信の勝敗を RunHistory に書かない経路では、配信の後に `NewsModel.SetLastStreamResult(bool won)` を呼ぶ。`NewsModel.ArcSlots`（予約枠と決まった分岐）、`NewsEventInstance.arcId / arcStep` でレポートに出せる。
